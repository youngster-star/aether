# 功能完整性检查（functional）

依据：Stage.md（阶段任务表 + 完成标准）、BackEnd-Plan.md（§5 API / §6 表结构）、UI-Plan.md（页面设计）。

## 1. 对照当前阶段完成标准（Stage.md）

1. 读 Stage.md §1.3 确认当前阶段，取该阶段"任务要点 + 完成标准"
2. 逐条核对：每条任务是否已实现？完成标准是否可达成？
3. 属于后置阶段的功能出现在当前代码中 → 不算 FAIL，但标注"提前实现，注意与计划一致性"

## 2. 功能正确性核对

| 检查点 | 依据 |
| --- | --- |
| 接口路径/方法/参数与 BackEnd-Plan §5.2 端点清单一致（含 /api/v1 前缀约定） | §5.1 |
| 表结构/字段与 §6 建表 DDL 一致（含 COMMENT 中文注释、软删除 status、时间字段） | §6.2 |
| 业务规则边界：如文章阅读数 IP 24h 去重、问卷 IP 1 份 + 改 2 次（30703）、AI 限额（30803）、订阅同 IP 多邮箱 | §4.6、§7.5、§5.2 |
| 前后端约定一致：错误码文案映射、VO 字段名、签名 URL 字段名（coverUrl/fileUrl） | UI-Plan §9.2、§11 |
| 防呆设计：空值/超长/非法字符/重复提交/并发提交 | BackEnd-Plan §12 |

## 3. 文档一致性（Stage.md §1.2 强制）

- 本次变更是否改了 API（路径/参数/返回结构）→ 必须已同步 BackEnd-Plan §5
- 是否改了表结构 → 必须已同步 BackEnd-Plan §6
- 是否改了页面/交互/组件 → 必须已同步 UI-Plan
- Stage.md §1.4 提交记录表是否已覆盖待推送内容（push 含代码变更时门禁 hook 强制校验，缺失即 FAIL）
- 文档未同步 → 本维度 FAIL（先改文档再改代码是硬规范）

## 输出格式

- 阶段完成标准逐条核对表（✅/❌/⚠️）
- 业务规则边界问题清单
- 文档同步检查结果
- 结论：PASS / FAIL
